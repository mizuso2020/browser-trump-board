# オンライン対戦 / 掲示板 / 募集中の部屋

2026-08-19 実装完了時点の記録。着手前の仕様案を、実装後の姿に書き換えたもの。

---

## 1. モードの構造

| モード | 意味 | 通信 |
|--------|------|------|
| `local` | スマホ1台を回す | 通信なし。`sessionStorage` のみ |
| `room` | 同じ場所で各自のスマホ | ルームAPI(HTTP) |
| `online` | 離れた場所 | ルームAPI(HTTP) — **`room` と同一経路** |

`room` と `online` は実装が同じ。各ゲームの分岐も例外なく
`room.mode === "room" || room.mode === "online"` の形になっている。
違いは表示の文言と参加リンクの `mode=` だけ。

### 対応モードの情報源は1つだけ

`js/game-registry.js` の `modesSoon` が唯一の情報源。**ここに載っていない
モードが使える**という意味（`modesSoon: ["local"]` なら1台だけ非対応）。

判定は `room.js` の `rejectUnsupportedMode()` を通す。かつてゲームIDを
直接列挙した条件が2箇所にあり、レジストリと食い違って
**将棋とナンバーリンクが「1台で遊ぶ」を選べるのに開始できない**状態を
生んでいた。列挙を復活させないこと。

現在 `modesSoon` を持つのは各自スマホ／オンライン専用の7タイトルのみ:
大富豪・爆弾・ブラックジャック・99・テキサスホールデム・
セブンカードスタッド・ファイブカードドロー。

### Firebase は使っていない

当初オンラインは Firebase で作る想定で、`canUseMultiDevice()` が
`isFirebaseConfigured()` を見ていた。設定が空のままだったため
オンラインが永久に塞がっていた。現在は Firebase 関連のコード・SDK読み込み・
設定ファイルをすべて削除済み。

同じ整理で `js/utils.js`（217行）も消した。`ensure-utils.js` と定義が完全に
重複していて、どのHTMLからも読み込まれていなかった。読まれないファイルを
直しても動作は変わらないので、残しておくと事故のもとになる。

## 2. 参加者トークン

役職・手札・お題・数字などの秘密は、本人（と進行役のホスト）だけが読める。

- ルーム作成・参加時に `token_urlsafe(24)` を発行し、`tokens.json` に保存
- クライアントは `localStorage` の `partyGames_roomToken_<CODE>_<playerId>` に保持
- 以後 `X-Room-Token` ヘッダーで本人確認

**キーにプレイヤーIDを含める**こと。ルームコードだけにすると、1台のブラウザで
複数人が入り直したときにトークンが混ざる。

再接続用の `resolve-player` はトークンを返さない。名前を言うだけでトークンが
手に入ると、なりすまして他人の秘密を読めるため。代償として、ゲーム進行中に
ブラウザのデータを消すと自分の秘密が読めなくなる。

`tokens.json` を持たない部屋は、この機能より前に作られたものとみなして
素通しする（進行中のゲームを壊さないため）。

## 3. 掲示板

### チャンネル

3つある。人狼以外のゲームでは `main` しか使わない。

| | `main`（議論） | `spirit`（霊界） | `wolf`（人狼の相談） |
|---|---|---|---|
| 生存者（人狼以外） | 読み書き | **返さない** | **返さない** |
| 生存者（人狼） | 読み書き | **返さない** | 読める。書けるのは夜だけ |
| 死亡者 | 読むだけ | 読み書き | **返さない** |

見せない先は画面で隠すのではなく、**APIが最初から返さない。**

### 誰がどこに書けるか

`writable_channels()` が一覧を返し、**先頭が既定**。クライアントは希望を
出せるだけで、一覧に無い先を指定しても既定へ落とされる。死んだ人が議論に、
人狼が昼に相談へ割り込む道を残さないため。

- 死亡者 → `("spirit",)`
- 生きている人狼・夜 → `("wolf", "main")` … **既定が相談側**。作戦を誤って
  全体に書く事故は取り返しがつかないため
- それ以外 → `("main",)`

相談を書けるのは `WOLF_TALK_PHASES = {"wolf_night"}` のみ。昼に私語させると
嘘の口裏合わせが他の人に見えないまま進み、ゲームが壊れる。**読むほうは昼も
許す**（前夜のログの読み返しは妨げない）。

狂人は人狼ではないので相談が見えない。死んだ人狼は霊界へ回り、生きている
人狼の相談には混ざれない。

### 判定に使うデータ

- 生死 … `public.json` の `gameState.alive`
- 役職 … `hostSecrets.json` の `roles`。チャンネルの出し分けにだけ使い、
  外へは返さない
- 夜かどうか … `public.json` の `phase`

対象は `LIVENESS_GAMES = {"werewolf"}` のみ。ポーカー系も `alive` を持つが、
あちらは「このハンドに残っているか」の意味なので、フォールドした人を霊界に
落とさないよう限定している。

### 送信先の選択（クライアント）

書ける先が2つ以上あるときだけタブを出す（実質、夜の人狼だけ）。状況が
変わったらサーバーの既定に戻す。「選択中がまだ有効なら維持」にすると、
夜になっても `main` が有効なままなので切り替わらない（実装時に一度踏んだ）。

### 制限値（`api/room_server.py`）

| 定数 | 値 | 意味 |
|------|-----|------|
| `MESSAGE_MAX_CHARS` | 200 | 本文の上限 |
| `MESSAGE_KEEP` | 200 | 1部屋の保持件数。超えたら古い順に破棄 |
| `MESSAGE_MIN_INTERVAL` | 0.8秒 | 同じ人の連投を抑える |
| `MESSAGE_CHANNELS` | main / spirit / wolf | チャンネルの種類 |
| `WOLF_TALK_PHASES` | `{"wolf_night"}` | 人狼が相談を書けるフェーズ |

保持件数は全チャンネル合算。相談や霊界が流れると議論のログも一緒に
押し出される点に注意。

### なりすまし対策

投稿者名は `player_display_name()` が `public.json` から引く。リクエストに
`name` や `playerId` を書いても無視される。

スタンプは `ALLOWED_STAMPS` の20種のみ。任意文字列を許すと本文の抜け道に
なるため、サーバー側の一覧が正。**`js/room.js` の `ROOM_STAMPS` と並びを
揃えること。**

本文は `escapeHtml()` を通して描画する。`<script>` を投稿しても文字列として
表示され、実行されない（実測確認済み）。

### UIの置き場所

掲示板は `#app` の外（`room.html` 直下）に置く。`room.js` の `render()` は
`#app` を作り直すため、中に入れると**同期のたびに入力中の文字が消える。**
1台モードでは全員が同じ画面を見るので表示しない。

## 4. 募集中の部屋

`rooms.html` + `js/rooms-page.js`。8秒ごとに `GET /rooms/open` を叩く。

載る条件は4つすべて:

1. `isOpen: true`（作成時に「公開して募集する」を選んだ）— **既定は非公開**
2. `phase === "lobby"`（まだ始まっていない）
3. 空きがある（`players < capacity`）
4. `ROOM_OPEN_STALE_SECONDS`（10分）以内に更新がある

返すのは部屋コード・ゲーム・人数・定員・更新時刻だけ。**参加者の名前は
募集判断に要らないので返さない。**

### 部屋の寿命

以前は掃除処理が一切なく、デプロイ時点で**84部屋がディスクに残留**していた。
現在は `GET /rooms/open` のついでに `sweep_stale_rooms()` を間引いて呼ぶ。

| 定数 | 値 |
|------|-----|
| `ROOM_STALE_SECONDS` | 3時間（これ以上更新が無い部屋を削除） |
| `ROOM_SWEEP_INTERVAL` | 10分（掃除を走らせる間隔） |

### 定員は二重管理になっている

`GAME_MAX_PLAYERS`（Python）と `maxPlayers`（レジストリ）を手で揃える必要が
ある。サーバーはJSを読めないため。**ここに無いゲームは既定の16人になり、
定員を超えて参加できてしまう。** 実際に2度やった:

- 大富豪・ブラックジャックなど公開中6タイトルが未登録だった
- 新規公開した7タイトルを追加し忘れ、ダウト(4人)が16人まで入れる状態になった

**ゲームを `live` にするときは必ず両方を更新すること。** 照合スクリプトは
`docs/` には置いていないが、23タイトル全件の一致を確認済み。

## 5. 迷惑行為への対処

### ホストのキック

ロビー中、ホスト以外に「追い出す」が出る。単に一覧から消すだけでは足りず、
次の2つが必要だった。

- `merge_players()` がホストの古い参加者一覧を合成し直し、**キックを
  取り消していた。** `public.kicked` に記録して戻さないようにしている
- 追い出した相手のトークンと `private/*.json` を削除する。残すと復帰できる

キックされた相手は再参加403・掲示板403・秘密403（実測確認済み）。

### 通報

発言単位で `POST /room/{code}/report`。参加者のみ、`REPORT_MIN_INTERVAL`
（10秒）に1回、理由は300文字まで。

`reports.jsonl` に1行ずつ追記し、**通報された発言そのものも残す**（部屋が
消えた後でも判断できるように）。

**自動でBANはしない。** 誤報や嫌がらせ通報で人を弾くほうが害が大きいため、
記録に徹し、その場の対処はホストのキックに任せる方針。

読むとき:

```
ssh -i ~/Downloads/my-shop-key.pem ec2-user@54.65.228.227 'cat /home/ec2-user/party-games-data/reports.jsonl'
```

### 表示名

`clean_name()` が制御文字を落とし、空白を畳んで12文字に切る。空白だけの
名前は400。クライアントの `maxlength` は開発者ツールで外せるため、
サーバー側で処理している。

NGワードによる名前・本文のフィルタは入れていない。すり抜けと誤検出の
両方が起きるうえ、通報とキックのほうが確実に効くため。

## 6. 同期と通信量

`GET /room/{code}` を **400ms間隔**でポーリングする（[sync.js](../js/sync.js) の
`subscribeServer`）。部屋の状態はここに全部入っているため、一番重い経路。

### 絵が入ると桁が変わる

お絵描き人狼の絵は `gameState.sharedDrawing` に base64 JPEG で入り、
`public.json` に含まれて配信される。実測値:

| 状態 | サイズ |
|------|--------|
| 白紙 | 4 KB |
| 1人が描いた後 | 45 KB |
| 4人が描いた後 | 101 KB |
| 8周ぶん | **138 KB** |

138KB のうち **99.6% が絵**（絵を除くと 0.5KB）。6人で実測して 120 MB/分、
1人あたり 20 MB/分。描画1ターン90秒で1人30MB、6人5分で約0.6GB になっていた。

### ETag で 304 を返す

定期的な書き込みは無く、`public.json` は操作したときしか変わらない。
225回のポーリングのうち絵が変わるのは提出の1回だけで、残りは同じ内容の
再ダウンロードだった。

`public_etag()` が `public.json` の中身から SHA-1 を作り、`If-None-Match` が
一致したら **304（本文0バイト）** を返す。

| | 従来 | 現在 |
|---|------|------|
| 6人合計 | 119.9 MB/分 | **8.0 MB/分** |
| 1人あたり | 19.98 MB/分 | **1.34 MB/分** |
| 304の割合 | 0% | 93%（静止中は100%） |

残る 8MB/分 は各自の初回取得ぶん。お絵描き人狼だけでなく全ゲームに効く。

### 実装上の注意

**`apiFetch` は使えない。** あちらは毎回キャッシュバスター `?_=時刻` を付ける
ため、条件付きリクエストが成立しない。ルーム取得だけ `loadServer` が専用に
処理し、304のときは `_roomCache` の内容を返す。

`cache: "no-store"` も条件付きの土台を消すので `no-cache` にしてある。

別オリジンから ETag を読むには `Access-Control-Expose-Headers: ETag` が要る
（`cors_headers()` で付けている）。nginx はそのまま通す（実測確認済み）。

ETag は中身のハッシュなので、更新すれば必ず変わる。mtime やサイズで
代用すると、同じ時刻・同じ長さの書き込みで更新を取りこぼす。

### 絵そのものは軽くできなかった（測定済み・現状維持）

`toDataURL("image/jpeg", 0.55)` / 720x540 を変える余地を調べたが、
**変えないほうがよいと結論した。** 同じ調査を繰り返さないよう記録しておく。

実際の流れ（前の絵を土台に読み込む → 描き足す → 書き出す）を8周再現した結果:

| 形式 | 8周目 |
|------|-------|
| **JPEG q0.55（現状）** | **115 KB** |
| PNG（可逆） | 404 KB |
| WebP q0.8 | 139 KB |

線が滑らかに描かれて色数が多いため、可逆圧縮がまったく効かない。
「線画だから PNG が向くはず」は誤り。現状の JPEG が妥当だった。

寸法を落とす案も見送った:

| 寸法 | q0.55 | q0.5 |
|------|-------|------|
| 720x540（現状） | 115 KB | 109 KB |
| 640x480 | 97 KB | 89 KB |
| 560x420 | 75 KB | 74 KB |
| 480x360 | 60 KB | 56 KB |

キャンバスの表示幅は `min(720px, 96vw)` で、**PCでは720pxそのまま**。
縮小すると拡大表示になってぼやける。ETagで再取得は止まっているため
節約できるのは1ゲームで数百KBにすぎず、絵がぼやける代償に見合わない。

本気で減らすなら画像ではなく**ストローク（線の座標）を送る**方式にする。
8周でも数KBに収まり劣化もしないが、`drawing-werewolf.js` の描画・同期を
作り直す規模になる。

## 8. 画像

52MB あったものを 3.3MB にした。**目標寸法は「CSSでの表示サイズ × 3」**。
3倍ディスプレイまで耐える。

| フォルダ | 前 | 後 | 形式 |
|----------|-----|-----|------|
| `cards` (54枚) | 35.4MB | 1.85MB | JPEG q92 / 384x576 |
| `wordwolf` | 4.2MB | 0.17MB | JPEG |
| `games` | 3.0MB | 0.14MB | JPEG |
| `shogi` (30枚) | 2.6MB | 0.50MB | **PNG のまま** |
| `roles` | 1.6MB | 0.36MB | JPEG |

### 透明を使っているかで形式を分ける

カードは 1024x1536 の RGBA PNG だったが、表示は 108x150、しかも
**アルファは54枚とも完全に不透明**だった。将棋駒だけは半透明の縁を
実際に使っているので PNG を維持している。

「PNGだから透明が必要」と決めつけると無駄が残り、一律 JPEG にすると駒の
縁が壊れる。**1枚ずつアルファの最小値を見て判断すること。**

### 背景だけ別扱い

`werewolf-background` は `background-size: cover` で全画面に広がるため、
一律縮小の対象から外して元寸(768x1376)で作り直した。それでも 111KB → 19KB。
表示サイズが CSS から読み取れない画像は個別に判断する。

### 拡張子を変えると参照が壊れる

`.png → .jpg` にしたので参照の更新が要る。**カード54枚と役職9種は動的に
組み立てていて grep では拾えない。** 静的な参照だけ直して満足すると、
実際に遊んだときに画像が出ない。

更新した場所:
`playing-cards.js`（カード名の生成）/ `werewolf.js`（役職・裏面）/
`wordwolf.js`（勝利カード）/ `game-registry.js`（アイコン10箇所）/
`style.css`（人狼テーマの背景）

### 制作用データは配信物に入れない

`images/roles/` に PDF と原稿シート（計4.4MB）が置かれ、どこからも参照されて
いないのに配信されていた。`design-source/` へ移動済み。

元画像は git 履歴に残っている（`git show <変換前のコミット>:images/cards/club_01.png`）。

## 9. デプロイ

**サーバーに git は入っていない。** 配信は
`/usr/share/nginx/html/games/` へのファイル転送。`~/party-games` は
`room_server.py` の置き場所にすぎず、静的ファイルは同期していない
（実際に `sync.js` の内容が食い違っていた）。

### 順序が重要

1. 静的ファイル（`*.html` / `js/*` / `css/*`）を先に配置
2. そのあと `api/room_server.py` を置いて `sudo systemctl restart party-games-room`

逆にすると、キャッシュを持つ利用者が**古い `sync.js` でトークンを送れず
403になり、自分の役職すら読めなくなる。** 検証中に実際に踏んだ。

### キャッシュ更新を忘れないこと

HTMLの `?v=` を上げないと、変更したJSが利用者に届かない。`sync.js` は
元々 `play.html` で `?v=` 無しだったため、付け忘れると特に危ない。

nginx はハイフン付きヘッダーを既定で転送するため、`X-Room-Token` のために
設定を変える必要はない（実測確認済み）。

### 戻すとき

デプロイ前に `/home/ec2-user/backup-<日時>/` を作っている。最後のパスは
`/home/ec2-user/.last-backup-path` にある。

## 10. 残っている検討事項

- **`reports.jsonl` が無制限に増える。** 溜まってきたら整理か上限が必要
- **4桁コードは総当たりで到達できる。** 秘密はトークンで守られているが、
  部屋への飛び入り自体は防げない。桁数を増やすか要検討
- **占い師など他の役職の専用チャンネルは無い。** 人狼だけ特別扱いしている。
  必要になったら `readable_channels()` の分岐を増やすことになる
お絵描き人狼の絵の重さは**測ったうえで現状維持**とした（6章に記録）。
形式変更も寸法縮小も割に合わない。減らすならストローク送信への作り替え。
